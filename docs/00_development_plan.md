# FallingDown 개발 계획서

> 버전 0.2 / 2026-08-21 (기술 스택 확정, 결정 대기 항목 해소 반영)
> 입력 문서: `fallingdown_game_design.md` v0.9.1 (프로덕트 정의)
> 본 문서는 HQ(프로듀서) 세션이 작성하는 전체 작업 계획이다. 실제 제작은 파트별 작업 세션이 HQ가 발행하는 지시문(`docs/instructions/`)을 받아 수행하고, HQ가 산출물을 검수한다.
> 이 문서의 결정은 기획서의 프로덕트 정의를 변경하지 않는 범위에서 이루어진다 (기획서 18장 원칙).

## 1. 운영 구조

| 역할 | 담당 | 산출물 위치 |
|---|---|---|
| HQ (프로듀서) | 본 세션 — 계획, 지시문 발행, 검수, 피드백 | `docs/` |
| 개발 파트 | 별도 작업 세션 | `game/` (웹 프로젝트) |
| 아트 파트 | 컨셉·목업은 HQ가 AI 도구로 제작, 3D는 사용자가 직접 제작 (Blender MCP / Tripo 등 AI 활용) | `art/` |
| 스토리 파트 | 별도 작업 세션 (HQ 검수) | `docs/story/` |
| 사운드 파트 | AI 생성 (BGM·SFX). 디렉션 문서는 HQ 작성 | `art/sound/` |

- 지시문 형식: 목적 → 범위(포함/제외) → 산출물 → 완료 기준(검증 가능한 항목) → 참조 문서. 한 지시문은 한 세션이 완주 가능한 크기로 발행한다.
- 모든 산출물은 이 저장소에 커밋한다. 검수는 HQ가 커밋 단위로 수행한다.

### 1.1 Git 운영 규칙

- 브랜치 전략: `main` = 검수 통과분만 존재하는 안정 브랜치. 각 세션은 `claude/<작업명>-<id>` 브랜치에서 작업한다.
- **각 세션의 작업이 끝날 때마다 HQ가 사용자에게 브랜치 처리 권장안(PR 생성 / 머지 / 폐기)을 보고하고, 사용자 승인 후 실행한다.** 세션이 임의로 머지하지 않는다.
- 새 작업 세션은 항상 최신 `main`에서 분기한다 (검수 전 브랜치 위에 다른 세션 작업을 쌓지 않는다).

## 2. 기술 스택 (확정)

**three.js 웹 스택: TypeScript + Vite + three.js + 앱인토스 WebView SDK(`@apps-in-toss/web-framework`)**

결정 근거 (2026-08-21 사용자 승인):

1. **개발 세션 자율성 (결정적 요인).** 웹 스택은 개발 세션이 클라우드 환경에서 빌드→실행→헤드리스 브라우저 자가 검증까지 완결할 수 있다. 사용자는 URL로 폰에서 확인만 하면 된다. Unity는 에디터가 필요한 모든 검증 루프가 사용자 로컬 머신에 종속된다 (Unity MCP도 로컬 에디터 실행이 전제).
2. **플랫폼 적합성.** 앱인토스 미니앱의 기본형이 WebView이며, 로그인·광고·인앱결제·리더보드가 WebView SDK로 공식 제공된다.
3. **에셋 파이프라인 정합.** 사용자의 3D 제작 도구(Blender / Tripo)의 표준 출력인 glTF가 three.js 네이티브 포맷. 툰 셰이딩은 MeshToonMaterial + 아웃라인 패스로 성립.
4. **용량.** three.js 코어 ~0.15MB vs Unity WebGL 런타임 ~10MB+ (Brotli 기준). 결정적 차이는 아니나 유리.

**Unity 전환 트리거 (M1 게이트에서 판정):** 중급 모바일 기기에서 60fps 미달이 최적화로 해소되지 않거나, 스킨 애니메이션·이펙트 파이프라인이 웹 스택에서 비용 과다로 판명되면 M2 착수 전에 Unity로 전환한다. 게임 로직 설계·밸런스 데이터·문서는 이식 가능하게 유지한다 (로직과 렌더링의 분리 — M1 지시문에 반영).

수용하는 비용: 엔진 제공 기능(게임 루프, 오브젝트 풀링, 씬 관리, 오디오)을 직접 구현. 시각 튜닝은 에디터 대신 인게임 디버그 패널로 수행.

### 2.1 용량 예산 초안 (100MB, 압축 전송 기준)

| 항목 | 예산 | 비고 |
|---|---|---|
| 코드 + three.js + SDK | 3MB | |
| 캐릭터·몬스터·보스 glTF (메시+리깅+애니메이션) | 20MB | 로우폴리, Draco/Meshopt 압축 |
| 텍스처 | 20MB | 툰 셰이딩 = 소형 램프/플랫 텍스처 위주, KTX2 압축 |
| 이펙트·파티클 | 5MB | 대부분 셰이더·프로시저럴로 |
| 사운드 (BGM+SFX, AI 생성) | 20MB | 압축 포맷, BGM 루프 짧게 |
| UI·폰트·컷씬 일러스트 | 15MB | 컷씬은 정지 일러스트+연출 (동영상 금지) |
| 예비 | 17MB | |

M2(버티컬 슬라이스) 종료 시 실측으로 갱신한다 (기획서 17.7 검증 항목).

## 3. 마일스톤 로드맵

기간 약속 대신 **게이트(검수 통과 조건)** 로 관리한다. 각 마일스톤 종료 시 HQ 검수 → 사용자 리뷰 → 브랜치 처리 권장안 보고 → 다음 지시문 발행.

### M1 — 그레이박스 프로토타입 (지시문: `docs/instructions/M1_graybox.md`)

아트 없이 프리미티브로 코어 루프를 성립시키고, 기획서 17장 검증 항목 1~6을 실측한다.

- 범위: 낙하 속도 다이얼, 탭/스와이프 입력 분류, 판정 링, 통과형·체류형 적, 깃털 게이지·도약, HUD 골격, 인게임 튜닝 패널, 모바일 브라우저 실행
- 게이트: 폰 브라우저에서 플레이 가능한 URL + 튜닝 리포트(오분류율 실측치, 3.0x 가독성 소견, 게이지 커브 실측, **중급 기기 FPS 실측 — Unity 전환 트리거 판정 포함**)

### M2 — 버티컬 슬라이스

아트·사운드 1세트를 실장해 최종 품질 1개 구간(튜토리얼 + 챕터1 스테이지1)을 완성한다.

- 선행 조건: M1 게이트 통과(스택 확정 판정 포함), 아트 디렉션·컨셉 승인(A1), 튜토리얼 스크립트 확정(S2), 3D 최소 세트(A3)
- 게이트: 기획서 16장 "재미 포인트 6감각" 중 1~4번이 체감되는 빌드, 용량 실측 리포트, 사용자(나) 플레이 승인

### M3 — 콘텐츠 프로덕션

- 범위: 챕터 1~3 전 스테이지·웨이브 데이터, A/B계열 전 타입, 중간·챕터 보스, 성장 시스템(우산/검/소켓/까마귀), 미션, 챕터 컷씬
- 웨이브·밸런스 데이터는 코드와 분리된 JSON 데이터로 작성해 HQ가 직접 검수·수정 가능하게 한다
- 게이트: 전 콘텐츠 플레이 가능 + 기획서 11장 레벨 설계 원칙 준수 검수 + 16장 6감각 전체 체감
- 병행: 수익화 설계 문서 (광고 + 인앱결제 — 배치 지점·상품 구성을 HQ가 설계해 사용자와 확정. 기획서의 자원 경제를 훼손하지 않는 범위)

### M4 — 플랫폼 연동·출시

- 범위: 앱인토스 WebView SDK 연동(로그인, 리더보드, 광고, 인앱결제), 성능·용량 최종 검증, [게임 출시 체크리스트](https://developers-apps-in-toss.toss.im/checklist/app-game) 대응
- 전제 현황: 토스 개발자 계정 생성·약관 동의 완료 → **게임 정보 등록과 심사 제출 단계부터 진행** (콘솔 등록 작업은 사용자 수행, HQ가 등록 정보·심사 대응 자료 준비)

## 4. 아트 파트 계획

컨셉·목업 단계는 HQ가 AI 생성 도구(ComfyUI, Higgsfield)로 직접 제작하고, 3D 제작은 사용자가 직접 수행한다 (Blender MCP / Tripo 등 AI 활용).

| 순서 | 산출물 | 게이트 |
|---|---|---|
| A1. 아트 디렉션 + 컨셉아트 패키지 | 스타일 정의(로우폴리+툰), 컬러 팔레트(고도별 배경 변화 포함), 레퍼런스 보드, **게임 분위기 키 비주얼, UI 포함 인게임 목업 화면 샘플**, 소녀(2스탠스)·까마귀 인형·지구 리빌 컨셉 | 사용자 승인 |
| A2. 적 컨셉 | A계열 6종 + B계열 4종 + 보스. **코드명·패턴·생애주기만 브리핑** (기획서 10장 "선입견 금지" 원칙) | 사용자 승인 |
| A3. 3D 제작 스펙 + 제작 | 모델별 폴리 예산·본 수·텍스처 크기, 애니메이션 리스트(낙하/베기/토글/도약/피격), glTF 내보내기 규격(Draco/Meshopt, KTX2). M2용 최소 세트(소녀+a-1+a-3) 우선 — 제작은 사용자, 스펙·검수는 HQ | M2 실장 검수 |

- A1·A2는 M1 개발과 병행 가능 (의존성 없음).

| 순서 | 산출물 | 내용 |
|---|---|---|
| S1. 스토리 바이블 | `docs/story/story_bible.md` | 미스터리의 전체 답("무엇이 소녀를 끌어당기는가, 소녀는 누구인가, 까마귀는 무엇인가"), 챕터 1~3 각각이 해소·확장하는 미스터리 1개씩의 배치, 결말 방향, 후속 시즌 여지 |
| S2. 튜토리얼 인트로 스크립트 | `docs/story/tutorial_script.md` | 기획서 3.1 튜토리얼 매핑 표를 컷 단위 연출 지시로 확장 — 컷별 화면 묘사, 대사, 조작 유도 타이밍, 120초 예산 배분 |

- 게이트: S1·S2 모두 사용자 승인 후 확정 (내러티브는 취향 관여도가 높으므로 HQ 단독 확정하지 않는다).

## 6. 사운드 파트 계획 (AI 생성)

- 방침: BGM·SFX 모두 AI 생성. 사운드 디렉션 문서(무드, 트랙 리스트, SFX 리스트 — 베기/히트스톱/링 진입 큐/도약/피격/UI)는 A1 승인 후 HQ가 작성.
- M1은 프로그래밍 비프음으로 충분 (링 진입 큐 검증용). 본 사운드는 M2부터 실장.
- 주의: 판정 큐(링 진입음)는 게임플레이 장치이므로 지연 실측 후 채택 (모바일 WebAudio 지연 확인).

## 7. 검수 기준 (HQ 공통)

1. **기획서 정합성:** 기획서 수치·규칙과 다르게 구현된 부분은 "튜닝 결과"인지 "임의 변경"인지 구분해 보고받는다. 임의 변경은 반려, 튜닝 결과는 기획서 개정으로 반영.
2. **기획서 16장 6감각:** 빌드 리뷰의 판정 기준.
3. **기획서 11.2 난이도 4축:** 레벨 데이터 검수 시 스탯 인플레 금지 원칙 위반 여부 확인.
4. **용량 예산:** 매 마일스톤 실측 보고 필수.
5. **로직-렌더링 분리:** Unity 전환 트리거 대비, 게임 로직·밸런스 데이터가 렌더러에 독립적인지 코드 검수에 포함 (M1~M2 동안 유지, M2 게이트에서 스택 최종 확정 후 완화 가능).
