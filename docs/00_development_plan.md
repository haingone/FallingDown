# FallingDown 개발 계획서

> 버전 0.1 / 2026-08-21
> 입력 문서: `fallingdown_game_design.md` v0.9.1 (프로덕트 정의)
> 본 문서는 HQ(프로듀서) 세션이 작성하는 전체 작업 계획이다. 실제 제작은 파트별 작업 세션이 HQ가 발행하는 지시문(`docs/instructions/`)을 받아 수행하고, HQ가 산출물을 검수한다.
> 이 문서의 결정은 기획서의 프로덕트 정의를 변경하지 않는 범위에서 이루어진다 (기획서 18장 원칙).

---

## 1. 운영 구조

| 역할 | 담당 | 산출물 위치 |
|---|---|---|
| HQ (프로듀서) | 본 세션 — 계획, 지시문 발행, 검수, 피드백 | `docs/` |
| 개발 파트 | 별도 작업 세션 | `game/` (Unity 프로젝트) |
| 아트 파트 | 컨셉은 HQ가 AI 도구로 직접 제작, 3D 제작은 스펙 문서화 후 수제작 | `art/` |
| 스토리 파트 | 별도 작업 세션 (HQ 검수) | `docs/story/` |

- 지시문 형식: 목적 → 범위(포함/제외) → 산출물 → 완료 기준(검증 가능한 항목) → 참조 문서. 한 지시문은 한 세션이 완주 가능한 크기로 발행한다.
- 모든 산출물은 이 저장소에 커밋한다. 검수는 HQ가 커밋 단위로 수행한다.

## 2. 기술 스택 (제안 — 확정 전 1건 확인 필요)

**제안: Unity + URP(툰 셰이딩) + WebGL 빌드 + 앱인토스 Unity SDK**

근거 (앱인토스 개발자센터 조사 결과):

- 앱인토스 미니앱은 웹 기반으로 동작하며 공식 지원 스택은 **WebView SDK / React Native SDK / Unity WebGL / Cocos Creator 3.8.7** 4종이다.
- Unity는 전용 적용 가이드와 SDK(C# API 레이어 + jslib 브리지)가 제공되어, C#만으로 로그인·광고·결제·리더보드·햅틱 등 플랫폼 기능을 연동할 수 있다.
- 본 게임은 3D(Z축 깊이) + 툰 셰이딩 + 파티클(속도선)·FOV 연출이 코어라서, 3D 파이프라인·에셋 최적화(메시 압축, 텍스처 아틀라스) 실적이 가장 두터운 Unity가 적합하다. Cocos Creator 3.8.7도 3D를 지원하나 툰 셰이딩·모바일 3D 최적화 자료가 상대적으로 적다.
- 빌드 용량: 앱인토스 가이드 기준 **128MB 미만 = 양호**. 기획서의 100MB 제한은 이보다 보수적이므로 100MB를 내부 예산으로 유지한다.

**개발 세션이 착수 시 확인할 것 (HQ 네트워크에서 개발자센터 직접 접근 불가):**

1. 개발자센터 [권장 Unity 엔진 버전](https://developers-apps-in-toss.toss.im/unity/guide/recommend-engine.html) 페이지에서 권장 버전 확인 후 프로젝트 생성 (확인 불가 시 Unity 6 LTS + URP로 시작하고 HQ에 보고).
2. iframe 방식은 보안 심사 반려 사유 — 공식 [Unity 포팅 가이드](https://developers-apps-in-toss.toss.im/porting_tutorials/unity.html) 경로를 따를 것.

### 2.1 용량 예산 초안 (100MB, WebGL 압축 빌드 기준)

| 항목 | 예산 | 비고 |
|---|---|---|
| Unity 엔진 런타임 + 코드 | 25MB | WebGL 빌드 기본 비용. 스트리핑 필수 |
| 캐릭터·몬스터·보스 메시/리깅 | 15MB | 로우폴리, 본 수 최소화 |
| 텍스처 | 20MB | 툰 셰이딩 = 소형 램프/플랫 텍스처 위주, 아틀라스화 |
| 이펙트·파티클 | 8MB | |
| 사운드 (BGM+SFX) | 15MB | 압축 포맷, BGM 루프 짧게 |
| UI·폰트·컷씬 | 10MB | 컷씬은 정지 일러스트+연출로 (동영상 금지) |
| 예비 | 7MB | |

M2(버티컬 슬라이스) 종료 시 실측으로 갱신한다 (기획서 17.7 검증 항목).

## 3. 마일스톤 로드맵

기간 약속 대신 **게이트(검수 통과 조건)** 로 관리한다. 각 마일스톤 종료 시 HQ 검수 → 사용자 리뷰 → 다음 지시문 발행.

### M1 — 그레이박스 프로토타입 (다음 지시문, `docs/instructions/M1_graybox.md`)

아트 없이 프리미티브(캡슐·구·박스)로 코어 루프를 성립시키고, 기획서 17장 검증 항목 1~6을 실측한다.

- 범위: 낙하 속도 다이얼, 탭/스와이프 입력 분류, 판정 링, 통과형·체류형 적, 깃털 게이지·도약, HUD 골격, 인게임 튜닝 패널, WebGL 빌드
- 게이트: 브라우저에서 플레이 가능한 빌드 + 튜닝 리포트(오분류율 실측치, 3.0x 가독성 소견, 게이지 커브 실측)

### M2 — 버티컬 슬라이스

아트·사운드 1세트를 실장해 최종 품질 1개 구간(튜토리얼 + 챕터1 스테이지1)을 완성한다.

- 선행 조건: M1 게이트 통과, 아트 디렉션 확정(4장), 튜토리얼 스크립트 확정(5장)
- 게이트: 기획서 16장 "재미 포인트 6감각" 중 1~4번이 체감되는 빌드, 용량 실측 리포트, 사용자(나) 플레이 승인

### M3 — 콘텐츠 프로덕션

- 범위: 챕터 1~3 전 스테이지·웨이브 데이터, A/B계열 전 타입, 중간·챕터 보스, 성장 시스템(우산/검/소켓/까마귀), 미션, 챕터 컷씬
- 웨이브·밸런스 데이터는 코드와 분리된 데이터 파일(ScriptableObject 또는 JSON)로 작성해 HQ가 직접 검수·수정 가능하게 한다
- 게이트: 전 콘텐츠 플레이 가능 + 기획서 11장 레벨 설계 원칙 준수 검수 + 16장 6감각 전체 체감

### M4 — 플랫폼 연동·출시 준비

- 범위: 앱인토스 SDK 연동(로그인, 리더보드, 광고·결제는 수익화 방침 확정 후), 성능 최적화, 용량 최종 검증, [게임 출시 체크리스트](https://developers-apps-in-toss.toss.im/checklist/app-game) 대응, 심사 제출
- 수익화 설계는 M3 진행 중 HQ가 별도 문서로 작성해 사용자와 확정한다 (기획서 18장 — 본 계획서 범위 외로 유보된 항목)

## 4. 아트 파트 계획 (AI 컨셉 → 수제작 3D)

컨셉 단계는 HQ가 이 세션의 AI 생성 도구(ComfyUI, Higgsfield)로 직접 제작하고, 3D 제작 단계는 스펙 문서로 넘긴다.

| 순서 | 산출물 | 게이트 |
|---|---|---|
| A1. 아트 디렉션 문서 | 로우폴리+툰 셰이딩 스타일 정의, 컬러 팔레트(낙하 배경의 고도별 변화 포함), 레퍼런스 보드 | 사용자 승인 |
| A2. 핵심 컨셉 아트 | 소녀(2스탠스: 우산/검), 까마귀 인형, A계열 6종 실루엣, 지구 리빌 키 비주얼 | 사용자 승인. **A계열 컨셉은 코드명만 전달** — 기획서 10장 "선입견 금지" 원칙에 따라 패턴·생애주기만 브리핑 |
| A3. 3D 제작 스펙 | 모델별 폴리 예산·본 수·텍스처 크기, 애니메이션 리스트(낙하/베기/토글/도약/피격), 용량 예산 배분 | HQ 검수 |
| A4. 3D 제작 | M2용 최소 세트(소녀+a-1+a-3) 우선 | M2 실장 검수 |

- A1·A2는 M1 개발과 병행 가능 (의존성 없음).
- 3D 수제작의 **제작 주체(외주/사용자 직접/기타)는 미정** — A3 완료 전까지 사용자와 확정 필요 (8장 인터뷰 항목).

## 5. 스토리 파트 계획 (전체 아크 + 튜토리얼 상세 선행)

| 순서 | 산출물 | 내용 |
|---|---|---|
| S1. 스토리 바이블 | `docs/story/story_bible.md` | 미스터리의 전체 답("무엇이 소녀를 끌어당기는가, 소녀는 누구인가, 까마귀는 무엇인가"), 챕터 1~3 각각이 해소·확장하는 미스터리 1개씩의 배치, 결말 방향, 후속 시즌 여지 |
| S2. 튜토리얼 인트로 스크립트 | `docs/story/tutorial_script.md` | 기획서 3.1 튜토리얼 매핑 표를 컷 단위 연출 지시로 확장 — 컷별 화면 묘사, 대사, 조작 유도 타이밍, 120초 예산 배분 |
| S3. 챕터별 컷씬 스크립트 | `docs/story/chapter{n}_cutscene.md` | M3 진행에 맞춰 챕터별 발행 |

- S1·S2는 M1과 병행하여 즉시 착수 가능. S2는 M2의 선행 조건.
- 게이트: S1·S2 모두 사용자 승인 후 확정 (내러티브는 취향 관여도가 높으므로 HQ 단독 확정하지 않는다).

## 6. 검수 기준 (HQ 공통)

1. **기획서 정합성:** 기획서 수치·규칙과 다르게 구현된 부분은 "튜닝 결과"인지 "임의 변경"인지 구분해 보고받는다. 임의 변경은 반려, 튜닝 결과는 기획서 개정으로 반영.
2. **기획서 16장 6감각:** 빌드 리뷰의 판정 기준.
3. **기획서 11.2 난이도 4축:** 레벨 데이터 검수 시 스탯 인플레 금지 원칙 위반 여부 확인.
4. **용량 예산:** 매 마일스톤 실측 보고 필수.

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| WebGL 모바일 성능 (3D + 파티클 + 60fps) | M1에서 저사양 기기 프레임 실측을 게이트에 포함. 툰 셰이딩은 라이팅 비용이 낮아 유리 |
| 탭/스와이프 오분류 (기획서가 지목한 최대 조작 리스크) | M1 최우선 검증 + 인게임 튜닝 패널로 임계값 실시간 조정 |
| WebGL 터치 입력 지연 | M1 빌드를 실기기(토스 샌드박스 또는 모바일 브라우저)에서 확인 |
| 용량 초과 | 예산표 기반 관리, 마일스톤별 실측 |
| 권장 Unity 버전 미확인 | M1 착수 시 개발 세션이 개발자센터에서 확인 (2장) |

## 8. 결정 대기 항목 (사용자 인터뷰 필요)

1. **3D 수제작 주체** — 외주 발주인지, 사용자 직접 제작인지, 다른 방안인지 (A3 전까지).
2. **수익화 방침** — 광고/IAP 구성 (M3 중까지. M4 범위에 영향).
3. **사운드 제작 방법** — AI 생성 / 라이브러리 구매 / 외주 (M2 전까지).
4. **토스 개발자 계정·심사 준비 현황** — 파트너 등록 여부 (M4 전까지).

이 4건은 각 시점 도래 시 HQ가 먼저 질문한다. 지금 결정하지 않아도 M1·A1·S1 착수에는 지장 없다.
