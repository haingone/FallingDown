## 0. 요약

- M1 코어(`src/core/`)를 이월하고 **뷰·판정을 HD-2D 다운 스크롤로 전환** 완료. 판정 투영은 원근 핀홀 →
  2D 평면(`Plane2D`)으로 교체, 적 동선은 소실점 접근 → **하단·사선 하단 진입 → 상방 통과**로 교체.
- HD-2D 5레이어 전부 동작(스카이/구름 3장/3D 유적/게임플레이/전경). **3D 오브젝트 레이어는 판정에 무관.**
- 베기 궤적 이펙트 구현 — 우산(넓은 호·폭 112pt·0.32초)과 검(가늘고 예리·폭 44pt·0.20초) 시각 차별화,
  히트스톱 40ms + 격파 파편. 전부 셰이더/프로시저럴 (텍스처 에셋 0).
- **게이지 배율 A/B 자동 실측 완료** (2장). 핵심: A(배율 적용) 고속 플레이는 **18.8초 / 판당 도약 5회**,
  B(미적용, 기본값)는 **41.5초 / 판당 도약 1회**. HQ 권장안 B가 "매 판의 감정 정점 1회" 설계와 일치.
- Playwright 자가 검증 **22/22 통과** (M1 12개 → 22개). 최초 병렬 실행 플레이크 보강 완료 (8장).
- 헤드리스 FPS: 네이티브 40.9 / 픽셀 스케일링 60 (소프트웨어 렌더링 참고치, 6장).
- 기획서 v2 수치 대비 **임의 변경 0건**. 미정값 선정 목록은 4장, 편차는 7장, 질문은 9장.

## 1. 기획서 v2 17장 검증 항목 1·3~8 실측/소견

### 1.1 (항목 1) 링 타이밍 가독성 — 2D

- 구현: 판정 링 상시 표시 + **링 진입 시 링 자체 펄스(밝기·색 변화)** + 적 색상 하이라이트(0x33ff88) +
  WebAudio 비프음(1180Hz/45ms). 링 안에 벨 수 있는 적이 있으면 링 색이 상시 초록 계열로 바뀐다.
- 자동 검증: 통과형 6기 추적 결과 **전부 화면 하단 밖(y < -belowWu×0.9)에서 스폰 → +y 상방 이동 →
  링 진입(진입 시 y<0, 즉 소녀 아래쪽) → 상단 프레임 아웃**. 진입각은 |최대| 16.4°(상한 38°) 준수.
  (`test-results/p1-2d-lifecycle.json`)
- **링 체류 시간 실측 0.800초 @1.0x** (기획서 기준 0.8초, 표본 5건 전부 오차 <0.1%).
  2D에서는 링을 지나는 직선의 **현(chord) 길이**로 통과 속도를 역산해 체류 시간 규칙을 정확히 성립시켰다.
- 소견: **2D 전환의 최대 소득은 "적이 어디 있는지"가 화면 좌표로 바로 읽힌다는 점**이다. M1(3D)에서는
  원근 때문에 링 진입 시점이 크기 변화로만 표현됐으나, 2D에서는 링과 적이 같은 평면 위에 있어
  거리·진입 시점이 기하학적으로 명확하다. 기획서 17.1의 "리스크 자체가 축소됨"은 구조적으로 확인된다.
  다만 **"체감상 충분히 읽히는가"는 실기기 플레이 필요** (특히 3.0x, 1.3 참조).
- WebAudio 지연은 헤드리스에서 무의미 — 튜닝 패널에 base/output latency를 계속 노출했으니
  폰 접속 시 패널에서 바로 읽을 수 있다.

### 1.2 (항목 2) 탭/스와이프 오분류 — M1 검증분 이월

- 분류기(`core/classifier.ts`)는 **무수정 이월**. 합성 제스처 400건 재실측 **오분류 0.0%** 유지.
- 임계값도 M1 검수 확정치 그대로: 24pt / 200ms / 0.5pt/ms.
- 실기기 재확인만 남았다 (사용자 협조 항목).

### 1.3 (항목 3) 3.0x 가독성 — 2D

- 3.0x에서 통과형 링 체류 0.3초, 체류형 공격 주기 1.5초 규칙은 선형 보간으로 유지, 자동 검증 통과.
- **접근 구간 실측**: 스폰(y = −7.2wu, 화면 하단 밖) → 링 가장자리까지 약 5.6wu.
  접근 속도 1.2wu/s × 배율이므로 **1.0x에서 약 4.7초, 3.0x에서 약 1.55초**의 인지 시간이 확보된다
  (M1 3D는 3.0x에서 1.67초 — 거의 동등하게 맞췄다). 접근 속도는 패널 손잡이(0.4~3.5wu/s).
- 오토플레이(판정 창 안에서만 베기)는 3.0x 유지로 **노히트 클리어**(62.2초, 평균 배율 3.23x) —
  판정 창이 기계적으로 성립함을 확인.
- 멀미: **3D의 FOV 72° 확대 대신 카메라 미세 줌아웃(1.0→1.06)** 으로 대체되어(기획서 v2 4장)
  시야 왜곡 요인이 사라졌다. 스크롤 속도·셰이크의 멀미 여부는 **실기기 평가 필요** —
  패널에 스크롤 속도 계수(0.2~3.0)·셰이크 강도(0~3, 0=끔)·줌아웃 배수(1.0~1.3)를 전부 노출했다.

### 1.4 (항목 4) 게이지 배율 규칙 — A/B 실측 → **2장에 별도 정리**

### 1.5 (항목 5) 체류형 혼잡도 — 2D

- 구현: 체류형은 **슬롯 기반 배치각**을 갖는다. 상한 4기를 화면 상방(+90°)을 중심으로 배치각
  (기본 300°)만큼 균등 분산하고, **전원이 같은 방향·같은 각속도로 함께 선회**해 슬롯 간 각 간격이
  항상 유지된다. 도착 지점에서 슬롯 각으로 0.4초에 걸쳐 정착(선회 진입)한다.
- 자동 검증(`p1-crowding.json`): 최종 웨이브에서 **체류형 4기 포화 재현**(60.6초 시점),
  정착 후 **최소 쌍간 각 60°, 최소 쌍간 거리 1.26wu**, **스프라이트 겹침 쌍 0**.
  같은 구간의 동시 활성 적 최대 9기(통과형 포함).
- 배치각 설계 근거: 화면 **하방(정하방 ±30°)을 비워** 통과형 진입 레인의 가독성을 확보했다.
  배치각을 360°로 올리면 하단이 막히고, 180°로 줄이면 상단이 뭉친다 — 둘 다 패널에서 실측 가능.
- 소견: 기하학적 겹침은 0이지만 **"타겟 우선순위가 읽히는가"는 주관 평가라 실기기 필요**.
  현재 우선순위 신호는 공격 예고(적색 발광 0.6초) / 링 내 하이라이트(초록) / 코드명 라벨 3종이다.

### 1.6 (항목 6) 스탠스 체감

- 판정 파라미터는 M1 잠정치 이월: 우산 궤적 폭 34pt·재판정 260ms / 검 14pt·110ms.
- **P1 신규: 이펙트로도 차별화**. 우산 = 폭 112pt의 넓은 호(궤적을 진행 방향 수직으로 17% 부풀림),
  잔광 0.32초. 검 = 폭 44pt의 거의 직선, 선단이 뾰족한 폭 프로파일, 잔광 0.20초, 연장 배수 2.3
  (검이 더 길고 얇게 화면을 가른다).
- 스크린샷 비교: `game/test-results/screens/04-slash-umbrella.png`, `05-slash-sword.png`.
- 소녀 실루엣 자세로도 스탠스가 구분된다 (접음: 접은 우산을 아래로 / 펼침: 머리 위 캐노피 + 뽑은 검).
- 실제 "손맛" 차이는 **실기기 평가 필요**.

### 1.7 (항목 7) HD-2D 렌더 성능 / 픽셀 스케일링 → **6장에 별도 정리**

### 1.8 (항목 8) 용량 예산

- 정적 빌드 실측: **JS 561.1KB(gzip 148.5KB) + HTML 4.8KB(gzip 1.8KB)**. M1 대비 +11.7KB(gzip) —
  증가분은 HD-2D 레이어·셰이더·베기 이펙트 코드이며 **텍스처/스프라이트 에셋은 여전히 0바이트**.
- 계획서 2.1 예산표의 "코드 + three.js + SDK 3MB" 대비 여유 큼.
- **본 항목의 진짜 변수는 스프라이트 시트 프레임 수**이며 P1 범위에서는 측정 대상이 없다
  (에셋 생성 금지). AD가 프레임 규격을 확정해야 예산 재수립이 가능하다 — 계획서 2.1·4장 그대로.

## 2. 게이지 배율 A/B 실측 (기획서 v2 7장 미결 항목 / 17장 항목 4)

튜닝 패널의 **게이지 배율 적용 ON/OFF 토글**(기본 OFF = HQ 권장안 (b))로 구현했고,
A/B × 고속/저속 4개 조건을 자동 실측했다. 측정 규칙: 게이지가 100%가 될 때마다 즉시 도약
(= 설계상 "감정 정점"의 실제 발생 횟수를 센다). 원자료 `game/test-results/p1-gauge-ab.json`.

| 모드 | 플레이 | 클리어 | **게이지 100% 도달** | 도달 웨이브 | 도달 시 격파 수 | **판당 도약** | 평균 배율 | 점수 |
|---|---|---|---|---|---|---|---|---|
| **A** 배율 적용 | 고속(접음 유지) | 59.8초 | **18.8초** | W2 | 8기 | **5회** | 3.22x | 22,079 |
| **A** 배율 적용 | 저속(펼침 유지) | 80.3초 | 55.3초 | W4 | 22기 | 1회 | 1.02x | 7,000 |
| **B** 배율 미적용 | 고속(접음 유지) | 62.0초 | **41.5초** | W4 | 23기 | **1회** | 3.23x | 21,901 |
| **B** 배율 미적용 | 저속(펼침 유지) | 80.1초 | 56.8초 | W4 | 22기 | 1회 | 1.02x | 7,214 |

### 소견

1. **A는 고속 플레이에서 판당 도약 5회.** 배율 곱으로 킬당 15%가 들어와 8킬 만에 게이지가 차고,
   이후에도 반복 충전된다. 기획서 11.3의 "게이지가 최종 웨이브~보스 구간에서 100% 도달",
   16장 3번 "게이지 100% 직후 포위망을 꿰뚫는 클라이맥스"와 정면 충돌한다.
   M1 3D 실측(18.8초/W2)이 2D에서도 **동일 수치로 재현**됐다 — 뷰 전환과 무관한 규칙 문제임이 확인된다.
2. **B는 속도와 무관하게 1회로 수렴**한다. 고속 41.5초(W4) / 저속 56.8초(W4) — 둘 다 최종 웨이브 구간이며
   기획서 11.3의 설계 의도와 일치한다. **"매 판의 감정 정점 1회"가 속도 선택과 독립적으로 보장된다.**
3. **고속 플레이의 보상은 배율(점수·비늘)로 이미 충분하다.** B에서도 고속 점수는 21,901 vs 저속 7,214로
   **3배 차이**다. 게이지에까지 배율을 곱하지 않아도 "빠르게 떨어질 용기 = 성장 속도" 고리는 유지된다
   (M1_review 3장 권장 근거의 실측 뒷받침).
4. 고속이 저속보다 게이지가 **빨리** 차는 것은 B에서도 유지된다(41.5 vs 56.8초). 접근 속도가 배율에
   비례해 적이 더 빨리 도달하기 때문이며, 이는 "속도가 리듬을 앞당긴다"는 자연스러운 결과다.

**개발 파트 소견: HQ 권장안 (b) = B(게이지만 배율 미적용) 채택을 지지한다.** 코드 기본값도 B이며,
채택 확정 시 기획서 8장 게이지 행·14장 깃털 행의 "배율 적용" 문구 삭제가 필요하다 (M1_review 3장 그대로).

> A/B 토글은 패널에 남겨 두었으므로 실기기에서 두 규칙의 **체감**도 바로 비교할 수 있다.

| 항목 | 고속 오토플레이 (접음 유지) | 저속 오토플레이 (펼침 유지) |

| 결과 | 클리어 (노히트, 재시작 0) | 클리어 |
| 클리어 시간 | 62.2초 | 82.4초 |
| 평균 배율 | 3.23x | 1.00x |
| 게이지 100% 도달 (기본값 B) | 41.7초 (W4) | 55.9초 (W4) |
| 격파 / 링 진입 | 47 / 47 | 47 |
| 통과 피해 / 이탈 | 0 / 1 | 0 |
| 동시 활성 적 최대 | 9기 | — |
| 웨이브 시작 시각 | 0.5 / 14.2 / 25.5 / 37.7 / 48.3초 | (접근 속도 ∝ 배율이라 연장) |

- 시퀀스 길이는 기획서 "90~120초" 대비 짧다(고속 62.2초). M1과 같은 이유로, 오토플레이가 모든 적을
  즉시 처치해 웨이브 종료(전멸) 시점이 앞당겨진 영향이다. 인간 플레이는 처치 지연만큼 늘어난다.
  저속 82.4초는 기준 하한에 근접한다.
- **격파 47 / 총 스폰 48**: 나머지 1기는 "이탈"(stray)이다 — 도약으로 소녀가 화면 안을 이동하는 동안
  링 밖을 지나쳐 프레임 아웃한 통과형으로, **피해 없이 소멸**한다(7장 편차 3번). 패널에 카운터를 노출했다.
- 도약 규칙 검증: 2.5초 무적 · 밀집 방향 자동 격파 · 깃털 미지급(A/B 공통) · 종료 후 3.0x 강제 ·
  1초 토글 잠금 · **화면 밖으로 나가지 않는 화면 내 비행** 모두 통과.
- 실패 경로 검증: 방치 시 통과 피해 누적 → HP 0 → 실패 → 자동 재시작(HP 전량 회복) 통과.

## 4. 기획서에 없는 미정값의 선정 목록 (임의 변경 아님 — 대부분 패널에서 조정 가능)

### 4.1 P1 신규 (2D 좌표계·동선)

| 값 | 선정치 | 사유 | 패널 |
|---|---|---|---|
| 화면 세로 = 월드 높이 | 10 wu | 2D 평면의 wu↔px 스케일 기준. 390×844에서 84.4px/wu | ✕ |

## 6. FPS·draw call·오버드로우 실측 (기획서 v2 17장 7)

**헤드리스 소프트웨어 렌더링 참고치** (`game/test-results/p1-perf-metrics.json`). 최종 웨이브(W5),
활성 적 8기, 3.0x, 체류형 포화 구간에서 측정.

| 정책 | 렌더 해상도 | FPS | 1% low | draw call | 레이어 | 풀스크린 패스 |
|---|---|---|---|---|---|---|
| 네이티브 | 390×844 | **40.9** | 13.3 | 31 | 5 | 4 |
| 픽셀 스케일링 (×3) | **130×281** | **60 (vsync 상한)** | 12.9 | 41 | 5 | 5 |

- **부하의 지배 요인은 프래그먼트(픽셀 채우기)다.** 해상도를 1/9로 줄이자 40.9 → 60fps(상한)로 올랐고
  draw call은 오히려 늘었다(블릿 패스 +1). 지오메트리·드로우콜은 병목이 아니다.
- **오버드로우 추정치 = 풀스크린 패스 4회** (스카이 1 + 구름 3). 여기에 게임플레이·전경 레이어의
  부분 오버드로우가 얹힌다. 픽셀 모드는 블릿이 1회 더 붙어 5회. 3D 오브젝트 레이어를 끄면(밀도 0)
  레이어 수가 5 → 4로 줄어드는 것까지 자동 검증에 포함했다.
- 구름 3장은 각각 3옥타브 fbm 노이즈를 풀스크린으로 계산한다 — **소프트웨어 렌더러에서는 이것이
  거의 전부의 비용**이다. 실제 모바일 GPU에서는 훨씬 저렴하지만, 저사양 기기 대응이 필요해지면
  ① 구름 레이어 수 감소 ② 노이즈 옥타브 2로 축소 ③ 구름을 저해상도 RT로만 그리기 순으로 여지가 있다.
- **Unity 전환 트리거(중급 기기 60fps 미달) 판정은 실기기 실측 전 보류.** 헤드리스 40.9fps는
  소프트웨어 래스터라이저 수치이므로 트리거 근거가 되지 못한다. 폰 접속 시 패널에서 즉시 확인 가능.
- **픽셀 스케일링 정책 소견**: 저해상도 RT + NearestFilter 정수 배 업스케일은 기술적으로 성립하며
  성능 이득이 명확하다(1/9 해상도). 다만 현재 씬은 픽셀 아트가 아니라 벡터형 실루엣·셰이더 그라데이션이라
  **계단 현상이 그대로 드러난다** (`screens/03-final-wave-pixel.png`). 픽셀 아트 채택 시에는 정합하지만,
  채택하지 않으면 이 경로는 "저사양 폴백"으로만 쓰는 것이 맞다. **AD 스타일 확정 대기 항목.**
  또한 CSS px 기준 정수 배율이므로 DPR이 정수가 아닌 기기에서는 최종 스케일이 정확히 정수가 아니다
  (기술 부채 3번).

## 7. 기획서 대비 편차 목록 (구현상 해석·연출 선택 — 전부 보고 대상)

1. **셰이크는 배경·전경 레이어에만 적용.** 게임플레이 레이어(④)를 흔들면 화면 좌표 판정(`Plane2D`)과
   렌더가 어긋난다 — 판정 투영은 셰이크를 모르기 때문이다. 판정-렌더 일치를 우선해 3D 오브젝트 카메라와
   전경 속도선만 흔든다. **줌아웃(1.0→1.06)은 판정 투영과 렌더가 같은 값을 공유**하므로 문제없다.
   전체 화면 셰이크가 필요하다는 판단이면 판정도 함께 흔드는 방식으로 바꿀 수 있다 (9장 질문 2).
2. **FOV → 줌아웃 대체**: M1의 FOV 60→72° 확대는 3D 전용 개념이라 제거하고, 기획서 v2 4장의
   "카메라 미세 줌아웃 1.0→1.06"으로 교체했다. 기획서 개편분을 그대로 따른 것이며 편차라기보다 이행이다.
3. **"이탈" 처리 신설**: 도약으로 소녀가 화면 안을 이동하는 동안 통과형이 링 근처를 지나지 못하고
   프레임 아웃하는 경우가 생긴다. **피해 없이 소멸**시키고 별도 카운터(stray)로 집계한다.
   기획서는 "링 통과 시(미처치) 접촉 1 피해"라 정의하므로 링을 통과하지 않은 적에 피해를 줄 근거가 없다.
   실측상 90초 시퀀스에서 1기(48기 중) 발생.
4. **체류형 접근은 소녀를 향한 유도**로 구현했다(통과형은 직선). "링 주변에 도달"이 생애주기 정의이고,
   도약으로 소녀가 이동해도 반드시 도달해야 하기 때문이다.
5. **체류형 선회는 전원 같은 방향·같은 각속도.** 개체마다 방향이 다르면 서로 교차하며 겹쳐 혼잡도가
   급격히 나빠진다(검증 항목 5의 목적과 충돌). 슬롯 간 배치각이 항상 유지되는 편이 가독성에 유리하다.
6. **실패 시 "즉시 재시작"**: M1과 동일하게 1.2초 실패 연출 후 자동 재시작 (상수 1개로 즉시 전환 가능).
7. **클리어 처리**: 지시문대로 최종 웨이브 격퇴 = 클리어 (중간 보스 범위 외). 클리어/실패 배너는
   전투 종료 후에만 화면 중앙에 표시.
8. **도약 중 입력 무시**, **웨이브 휴지기에도 콤보·속도·게이지 정상 동작**: M1 편차 5·6 그대로 유지.
9. **팔레트는 부록 A-1 "청록 낮 하늘" 1종만** 구현했다 (챕터 팔레트 시스템은 P1 범위 외).
   프로덕션 색은 AD 소관이며 코드상 `SkyPalette` 1개 객체 교체로 바뀐다.

> M1 검수 4장에서 "M2에서 필수"로 지정한 **편차 2(수직 구도 → 등 뒤 상방 구도 복원)** 는
> 기획서 v2.0의 HD-2D 전면 개편으로 **소멸**했다. 고정 프레임 2D 뷰가 확정 사양이므로
> 카메라 행렬 일반화(M1 기술 부채 2번)도 함께 소멸한다.

### 플레이크 보강 (M1 검수 1장 지적)

M1의 실패 원인은 **첫 렌더/셰이더 컴파일 중 이벤트가 지연돼 60ms 탭의 접촉 시간이 200ms 임계를
넘긴 것**으로 추정된다. 다음 4단계로 보강했다 (`tests/helpers.ts`).

1. `page.goto(..., { waitUntil: 'load' })`
2. `__fd` 훅 노출 대기
3. **`__fd.ready` 대기** — 첫 렌더 2프레임 완료(셰이더 컴파일 포함) 후에만 true
4. **rAF가 실제로 돌고 있는지 확인** (`__fd.frames` 증가) + 입력 테스트는 FPS 산출 가능 시점까지 추가 대기
5. 그럼에도 환경 스톨로 접촉 시간이 왜곡될 수 있으므로, **탭 테스트는 "실제 접촉 시간이 임계 내인 시도"가
   나올 때까지 최대 4회 재시도**하고 그 시도의 분류 결과를 검증한다 (분류기를 검증하지, 스케줄러를 검증하지 않는다).

검증: 기본 설정(`workers: 1`)으로 **3회 연속 22/22 통과**. 추가로 `--workers=4` 병렬 실행에서도
21/21 통과(FPS 실측 1건은 자동 skip — 병렬 시 실시간 FPS 측정이 무의미하므로 명시적으로 건너뛴다).

   **실제 도약 시간이 격파 수만큼 늘어난다**(실측 최대 약 +0.6초). M1부터의 동작이라 규칙 변경 없이
   그대로 두었다. (a) 현행 유지 (b) 도약 중 히트스톱 생략 (c) 도약 중 히트스톱 단축 중 어느 쪽인가?
   개발 파트 권장은 (b) — 연속 자동 격파 구간의 스터터가 도약의 질주감을 해친다.
4. **"이탈" 처리**: 7장 편차 3번. 링을 스치지 못하고 프레임 아웃한 통과형을 무피해 소멸로 두었다.
   설계상 문제없는가? (도약 중에는 어차피 무적이므로 실질 영향은 없다)
5. **체류형 배치각의 기준 방향**: 화면 상방을 중심으로 배치각을 벌려 하단 진입 레인을 비웠다.
   기획서에 방향 규정이 없어 가독성 기준으로 정했다 — 의도와 맞는가?
6. **픽셀 스케일링 채택 여부**: 6장 소견대로 기술적으로는 성립하나 **AD 스타일 확정이 선행**되어야 한다.
   P2 착수 전 AD 결정 일정이 필요하다.

## 10. 다음 마일스톤에 넘기는 기술 부채·우려 사항

1. **실기기 실측 공백 (최우선)**: FPS·오분류 체감·오디오 지연·멀미·링 타이밍 체감·혼잡도 가독성·손맛 전부
   헤드리스 참고치다. **`npm run dev` 후 폰 접속(README 절차) → 튜닝 패널 수치 확인 + 몇 판 플레이**가
   P1 게이트의 남은 절반이며, 사용자 판정("2D 베이스로 밸런스를 잡을 수 있겠다")의 근거가 된다.
2. **도약 중 히트스톱 누적** (9장 질문 3). 결정에 따라 상수 1개 또는 조건 1줄.
3. **픽셀 스케일링의 정수 배율 정확도**: CSS px 기준으로 정수 배율을 잡으므로 DPR이 비정수인 기기
   (예: 2.75)에서는 최종 화면 배율이 정확한 정수가 아니다. 픽셀 아트 채택이 확정되면 DPR을 1로 고정하고
   디바이스 픽셀 기준으로 재계산해야 한다.
4. **구름 셰이더 비용**: 6장 참조. 저사양 기기 대응 시 축소 경로를 미리 정해 두었다(레이어 수·옥타브·RT).
5. **3D 오브젝트 레이어의 아트 방향 미정**: 현재는 프리미티브 조합(아치·계단·잔해) 3종 + 단색 + 안개다.
   실제 유적 모델링 주체·규격은 AD 마일스톤에서 확정해야 한다 (계획서 4장).
6. **a-2 지그재그·편대 간격 등 연출성 상수**: 코드 상수 유지 (밸런스 아닌 연출 판단).
   레벨 디자인 본격화(P3) 시 데이터 승격 여부 결정 필요. M1에서 넘어온 그대로다.
7. **iOS Safari 쿼크 미검증**: Pointer Events·AudioContext 잠금 해제·safe-area 대응은 구현했으나
   실기 미확인 (계획서 8장 리스크 유지).
8. **오분류 "의심" 휴리스틱**: 실플레이 오분류율은 의도를 모르므로 추정치다 (M1 그대로).
9. **웨이브 데이터는 M1 이월분 그대로**다. 2D 접근 시간이 3D와 다르므로 템포 재설계 여지가 있으나,
   "임의 변경 0건" 원칙에 따라 손대지 않았다. 실기기 플레이 후 템포 조정이 필요하면 `waves.json` 단독 수정으로 끝난다.
