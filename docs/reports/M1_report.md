# M1 그레이박스 튜닝 리포트

> 작성: 개발 파트 세션 / 2026-08-21
> 지시문: `docs/instructions/M1_graybox.md` (r2) / 기획서: `fallingdown_game_design.md` v0.9.1
> 산출물: `game/` (TypeScript + Vite + three.js, npm lockfile 포함)
> 측정 환경: 클라우드 Linux 컨테이너, 헤드리스 Chromium(Playwright), 뷰포트 390×844.
> **실기기(폰) 실측은 본 환경에서 불가 — 사용자 협조 필요 항목으로 별도 표기.**

## 0. 요약

- 코어 루프(가속/감속 다이얼 × Z축 스와이프 × 도약) 성립. Playwright 자가 검증 **14/14 통과**.
- 오분류율(합성 제스처 400건): **0.0%** — 임계값 24pt/200ms **기본값 유지**.
- 게이지 100% 도달: 저속(1.0x) 플레이 **80.1초 중 54.0초(W4 압박 구간)** = 기획 의도 근접.
  고속(평균 3.2x) 플레이 **18.8초(W2)** = 배율 곱 적용으로 조기 도달 → **질문 1** (핵심 논점).
- 헤드리스 FPS 60(vsync 상한), draw call 44~48. Unity 전환 트리거 판정은 **실기기 실측 전 보류**,
  다만 부하 특성상 웹 스택 성립 가능성이 높다는 소견 (5장).
- 기획서 수치 대비 **임의 변경 0건**. 기획서에 없는 미정값의 선정 목록은 4장, 질문은 7장.

## 1. 기획서 17장 검증 항목 1~6 실측/소견

### 1.1 판정 링 깊이 인지

- 구현: 판정 링 상시 표시 + 링 진입 시 적 색상 하이라이트(밝은 초록 0x33ff88, 명도 대비 큼) +
  WebAudio 합성 비프음(1180Hz/45ms) 진입 큐.
- 소견: 그레이박스 기준 하이라이트 명도 차는 충분히 크다. 다만 3.0x에서 통과형 체류 창이 0.3초라
  시각 인지만으로는 늦고 **사운드 큐 의존도가 높은 구조** — 기획서 17.1의 해법 후보(명도·사운드 큐 강화)가
  실제로 필요함을 확인. 오판(원근만으로 벨 수 있다고 착각) 빈도는 주관 평가라 **실기기 플레이 필요**.
- WebAudio 지연: 헤드리스에서는 오디오 파이프라인이 실기기와 달라 수치가 무의미. 튜닝 패널에
  base/output latency 표시를 넣어 두었으니 **폰 접속 시 패널에서 바로 읽을 수 있음**.

### 1.2 탭/스와이프 오분류율 (목표 3% 이하)

- 방법: 분류기를 단일 모듈(`src/core/classifier.ts`)로 격리, 전 입력의 근거 수치(이동량·시간·최대 속도) 기록.
  인간형 합성 제스처 400건(탭 200: 접촉 40~180ms·떨림 0~12pt / 스와이프 200: 길이 40~240pt·시간 70~280ms·곡률 포함)을
  시드 고정 RNG로 주입.
- **실측: 오분류 0건 / 400건 = 0.0%** (탭→스와이프 0, 탭→무효 0, 스와이프→탭 0, 스와이프→무효 0).
- 최종 임계값: **24pt / 200ms 기본값 유지** + 속도 임계 0.5pt/ms(미정값, 4장). 실제 포인터 이벤트 경로
  (pointerdown→move→up)도 별도 3케이스로 검증 통과.
- 한계: 합성 모델은 "의도"를 알고 만든 제스처라 실손가락의 경계 사례(짧고 빠른 플릭, 떨리는 탭)를
  완전히 대변하지 못함. 인게임 통계(오분류 의심 휴리스틱: 임계 근접 탭, 히트 0의 짧은 스와이프)를
  패널에 노출했으니 **실기기 플레이 후 재측정 권장**.

### 1.3 3.0x 가독성

- 3.0x에서 통과형 체류 0.3초·체류형 공격 주기 1.5초 규칙은 선형 보간으로 구현, 자동화 검증 통과.
- 오토플레이(판정 창 안에서만 베기)는 3.0x 유지 상태로 **노히트 클리어 성공** — 판정 창이 기계적으로는
  성립함을 확인. "인간이 반응 가능한가"와 FOV 72° 멀미 여부는 **실기기 평가 필요**.
- 참고: 3.0x에서 스폰→링 도달이 약 1.67초(접근 40wu ÷ 8wu/s×3)라 원경 인지 시간 자체가 짧다.
  실기기에서 어렵다고 판명되면 접근 속도 기본값(패널 노출)을 낮추는 것이 첫 번째 튜닝 손잡이.

### 1.4 텐션 커브 (게이지 100% 도달 시점)

- 웨이브 데이터: 하급 40기 / 중급 8기, 90초급 5웨이브 (기준 "하급 최소 26기" 충족. `src/data/waves.json`).
- **저속 플레이(펼침 유지, 1.0x 고정·배율 1.0)**: 클리어 80.1초, 게이지 100% = **54.0초, W4 압박 구간**
  (요구 20킬 시점). 기획 의도 "최종 웨이브~중간 보스 구간 도달"보다 반 웨이브 정도 이르지만 근접.
- **고속 플레이(접음 유지, 평균 배율 3.22x)**: 클리어 61.7초, 게이지 100% = **18.8초, W2 구간**.
  "하급 1기 = 5%(배율 곱 적용)" 규칙 때문에 3.0x에서는 킬당 15%로 약 7킬 만에 충전됨.
- 소견: 배율 곱이 게이지에 걸리면 고속 플레이는 판당 도약 2~3회가 가능해져 "매 판의 감정 정점 1회"
  설계와 어긋날 수 있다. **질문 1로 회부** (규칙 변경은 하지 않고 지시문 문언대로 곱 적용 구현).

### 1.5 체류형 혼잡도 (상한 4기)

- 상한 4기 + 초과분 스폰 대기열 구현·검증 통과. 최종 웨이브에 체류형 4기(a-4×2, a-5×2)를 배치해
  통과형 동시 상황을 재현 가능하게 함.
- 소견: 오토플레이는 체류형을 즉시 처치해 포화가 짧다. "타겟 우선순위가 읽히는가"는 주관 평가 —
  **실기기 플레이 필요.** 그레이박스에서는 공격 예고(적색 발광 0.6초)가 유일한 우선순위 신호인데,
  통과형 하이라이트(초록)와 색으로 구분되는 점은 긍정적.

### 1.6 스탠스 체감

- M1 지시문대로 파라미터 차이로만 구현: 우산(접음) 궤적 폭 34pt·재판정 260ms / 검(펼침) 폭 14pt·재판정 110ms
  (4장 미정값). a-4(2타)는 검 스탠스가 재판정 간격 덕에 유리 — 기계적 차별화는 성립.
- 스와이프 궤적을 스탠스별 폭·색으로 오버레이 표시해 체감 차이를 보조. 실제 "손맛" 차이는 **실기기 평가 필요**.

### (참고) 17.7 용량 예산

- 정적 빌드 실측: JS 530.4KB(gzip **136.8KB**) + HTML 4.6KB. 예산표의 "코드+three.js+SDK 3MB" 대비 여유.

## 2. 오분류율과 최종 임계값

1.2 참조. **최종 임계값: 이동 24pt / 접촉 200ms / 속도 0.5pt/ms — 기획서 기준값에서 변경 없음.**
튜닝 패널에서 실시간 조정 가능 (8~60pt, 80~400ms).

## 3. 90초 시퀀스 실측 (자가 검증 수치)

| 항목 | 고속 오토플레이 (접음 유지) | 저속 오토플레이 (펼침 유지) |
|---|---|---|
| 결과 | 클리어 (노히트, 재시작 0) | 클리어 |
| 클리어 시간 | 61.7초 | 80.1초 |
| 평균 배율 | 3.22x | 1.00x |
| 게이지 100% 도달 | **18.8초 (W2)** | **54.0초 (W4)** |
| 격파 | 48/48 | 48/48 |
| 웨이브 시작 시각 | 0.2 / 14.2 / 25.4 / 37.4 / 48.1초 | (접근 속도 ∝ 배율이라 약 1.3배 연장) |

- 시퀀스 길이가 "90~120초" 기준 대비 짧은 편(고속 61.7초): 오토플레이가 모든 적을 즉시 처치해
  웨이브 종료(전멸) 시점이 앞당겨진 영향. 인간 플레이는 처치 지연만큼 늘어난다.
- 도약 규칙 검증: 2.5초 무적·밀집 방향 자동 격파·깃털 미지급·종료 후 3.0x 강제·1초 토글 잠금 모두 통과.
- 실패 경로 검증: 방치 시 통과 피해 누적 → HP 0 → 실패 → 자동 재시작(HP 전량 회복) 통과.

## 4. 기획서에 없는 미정값의 선정 목록 (임의 변경 아님 — 전부 패널에서 조정 가능)

| 값 | 선정치 | 사유 |
|---|---|---|
| 스와이프 속도 임계 | 0.5pt/ms | 기획서 5장 "또는 속도 임계 초과"의 수치 미정. 빠른 플릭(24pt 미만) 구제용 |
| 우산/검 궤적 판정 폭 | 34pt / 14pt | 우산 "넓고 호쾌" vs 검 "좁고 정밀"의 초기 대비값 |
| 우산/검 재판정 간격 | 260ms / 110ms | 검 "연격 빠름" 구현. a-6 패링 창(0.5초, M2+) 공략을 검이 담당하도록 260>500/2>110 배치 |
| a-5 본체 요구 베기 | 1회 | 기획서 미정. 노출 창(1초)이 난이도라고 판단 |
| a-5 투사체 속도 | 2.2wu/s | 링 가장자리→소녀 약 0.8초 — 요격 반응 창 확보 |
| 도약 비행 속도 | 16wu/s | 2.5초 내 화면 내 밀집 지점 왕복 가능 수준 |
| 격파 점수 | 하급 100 / 중급 300 / 투사체 50 | 기획서에 점수 테이블 없음. 배율 곱연산만 준수 |
| 스폰 거리 / 접근 속도 | 40wu / 8wu/s×배율 | 1.0x에서 스폰→링 5초, 3.0x에서 1.67초 |
| 판정 링 반경 / 판정 창 깊이 | 1.6wu / 2.0wu | 화면 폭 대비 링 지름 약 70% |
| 히트스톱 | 40ms | 기획서 범위 30~50ms의 중앙값 |

## 5. FPS·draw call 실측과 Unity 전환 트리거 소견

- **헤드리스 실측 (참고치)**: 최종 웨이브·파티클 최대 상태에서 FPS 60(vsync 상한 고정),
  1% low 15~40(소프트웨어 렌더링 노이즈로 측정마다 변동 큼), **draw call 44~48**, 활성 적 8기.
- 부하 특성: 지오메트리 총량 극소(구체 64·라벨 스프라이트·라인 90·박스 36), 드로우콜 50 미만,
  GC 스파이크 방지용 오브젝트 풀링 적용. 이 규모는 중급 모바일 GPU에서 여유가 큰 수준이다.
- **소견: Unity 전환 트리거(중급 기기 60fps 미달) 발동 근거 없음 — 단, 판정은 실기기 실측 후 확정 권장.**
  아트 실장(스킨 애니메이션·툰 셰이딩+아웃라인 패스·파티클 증가) 후가 진짜 시험대이므로 M2 게이트에서
  재측정이 필요하다. 폰 접속 시 튜닝 패널의 FPS/1% low/draw call 표시로 즉시 확인 가능.

## 6. 기획서 대비 편차 목록 (구현상 해석·연출 선택 — 전부 보고 대상)

1. **실패 시 "즉시 재시작"**: 1.2초 실패 연출 후 자동 재시작으로 구현 (무맥락 리셋 방지. 즉시로 바꾸려면 상수 1개).
2. **카메라 구도**: 기획서 4장 "등 뒤 상방"의 비스듬한 구도 대신 **낙하축 정렬 수직 구도**로 구현.
   사유: 화면 공간 스와이프 판정과 렌더 카메라를 동일한 순수 투영으로 닫아 로직-렌더링 분리를
   유지하기 위함. 부작용: 캡슐(소녀)이 위에서 본 원형으로 보여 자세 실루엣이 죽는다. M2에서
   비스듬한 구도 복원 시 판정 투영도 일반 카메라 행렬로 확장 필요 (기술 부채 항목).
3. **링 반경 튜닝 ↔ 체류 시간**: 기획서 12.1 "링 반경 확대 = 체류 시간 증가와 등가"를 적용해,
   패널에서 링 반경을 키우면 통과형 체류 시간이 비례 증가.
4. **링 진입 시 속도 불연속**: 접근 속도(8wu/s×배율)와 링 내 통과 속도(판정 창 깊이 ÷ 규정 체류시간)가
   달라 진입 순간 감속이 보인다. "링에서 벨 시간"이 시각적으로 생기는 효과 — 기획서는 두 값을 독립
   정의하므로 불연속은 필연. 거슬리면 M2에서 완만화.
5. **도약 중 입력**: 스와이프·탭 모두 무시 (기획서 "발동 후 자동 진행, 조작 불요" 해석).
6. **웨이브 휴지기**: 콤보·속도·게이지 시스템은 휴지기에도 정상 동작 (기획서 11.3 "토글 판단의 시간" 취지).
7. **클리어 처리**: 지시문대로 최종 웨이브 격퇴 = 클리어 (중간 보스 없음). 클리어/실패 배너는 전투 종료
   후에만 화면 중앙에 표시 (기획서 15장 "전투 공간 UI 금지"는 전투 중 기준으로 해석).

## 7. 기획서에 대한 질문 (구현은 문언대로 진행, 답변에 따라 수치/규칙 조정)

1. **[핵심] 게이지 배율 곱**: "하급 1기 = 5% (배율 곱 적용)"(지시문 6, 기획서 7장 곱연산 규칙)으로
   3.0x 플레이는 약 7킬 만에 게이지 100%가 되어 W2에서 도약이 터진다 (실측 18.8초). "클라이맥스에서
   도약 유도"(11.3) 의도와 충돌하는데, (a) 곱 유지+요구량 상향, (b) 게이지만 배율 미적용, (c) 현행 유지
   (고속 플레이 보상으로 인정) 중 어느 방향인가?
2. **콤보 리셋 조건**: 기획서 7장은 "피격/베기 미스 시 리셋"만 명시 — 3.0x에서 감속해도 콤보가 유지되는
   현행(문언대로, 적립만 중지)이 맞는가, 아니면 3.0x 이탈 시 리셋인가?
3. **빈 스와이프**: 적이 없을 때의 스와이프도 "베기 미스"로 콤보를 리셋하는가? (현행: 히트 0이면 전부 미스)
4. **a-5 본체 요구 베기 횟수**: 미정 → 1회로 구현. 확정 요망.

## 8. 다음 마일스톤에 넘기는 기술 부채·우려 사항

1. **실기기 실측 공백**: FPS·오분류율·오디오 지연·멀미·판정 체감 전부 헤드리스 참고치.
   **`npm run dev` 후 폰 접속(README 절차) → 튜닝 패널 수치 확인**이 M1 게이트의 남은 절반.
2. **카메라 일반화**: 수직 구도 전제의 순수 투영(6장 2번) — 비스듬한 구도 도입 시 뷰·프로젝션 행렬
   기반으로 확장 필요 (로직-렌더링 분리는 유지 가능, 작업량 소).
3. **iOS Safari 쿼크 미검증**: Pointer Events·AudioContext 잠금 해제·safe-area 대응은 구현했으나
   실기 미확인 (계획서 8장 리스크 그대로 유지).
4. **히트스톱 중 입력**: 히트스톱(40ms) 동안 시뮬레이션 시간이 멈춰 재판정 간격 계산이 사실상 연장됨.
   연출과 판정의 상호작용은 실기기 손맛 평가와 함께 재검토.
5. **오분류 "의심" 휴리스틱**: 실플레이 오분류율은 의도를 모르므로 추정치다. M2에서 토글 직후 즉시
   재토글 같은 행동 신호를 보강하면 정밀해진다.
6. **a-2 지그재그 진폭·주기, 편대 간격 등 연출성 상수**: 코드 상수로 두었다 (밸런스 아닌 연출 판단).
   레벨 디자인 본격화(M3) 시 데이터로 승격 여부 결정 필요.
